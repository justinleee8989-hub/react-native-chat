# PC 端与 Web 端完整测试说明 — 2026-11-18

手机原生端（Android Release）已在 `perf` 分支完成会话进入优化和整改回归，结论见 [CURRENT_ACCEPTANCE.md](CURRENT_ACCEPTANCE.md) 与 [REFACTOR_REGRESSION_2026-11-18.md](REFACTOR_REGRESSION_2026-11-18.md)。本轮对浏览器版本做一次完整测试：覆盖全部页面和主要业务流程，并重点验证 11-17 之后为手机端做的改动在浏览器上没有回退。

测完后填写 `PC_WEB_FULL_RESULTS_2026-11-18.md`（模板见第七节），证据放到 `docs/openim/evidence/2026-11-18-pc-web-full/`，提交并推送到 `perf`。

## 一、范围和口径

| 端 | 含义 | 基线视口 | 追加检查 |
|---|---|---|---|
| **PC** | 桌面浏览器，宽度 ≥ 900px，走桌面布局（左侧导航 + 主从分栏） | 1280×720 | 1440×900；**900px 与 899px 两侧**（布局切换边界） |
| **Web（H5）** | 手机浏览器，宽度 < 900px，走手机布局（底部四个标签） | 390×844 | 320×568 窄屏；**真实手机浏览器**（iOS Safari、Android Chrome 各一台，抽查第五节标 ★ 的用例） |

- 两端是同一个 Expo Web 产物（`web.output=single`），区别只在宽度。PC 上还有"手机预览"模式（宽屏下显示手机外框），归在 PC 的布局用例里测。
- 只用**独立 QA 账号 A / B / C** 和 QA 群；破坏性操作（解散、转让、清空、删除好友、改密码）只在本轮**新建**的 QA 群或 QA C 上执行。不碰原体验账号、原群和原消息。
- **不在本轮范围**：录音、录像（按约定由用户自测）；真实外部邮件 / 短信投递；手机离线推送；原生 Android/iOS（已单独验收）；Explore 示例页。
- "通过"只代表实际打开并操作过的页面和状态，不能用接口成功或自动测试代替浏览器结果。

## 二、环境准备

### 版本

| 仓库 | 分支 | 说明 |
|---|---|---|
| react-native-chat | `perf`（不早于 `8885e83`） | 记录实际测试的提交号 |
| chat | `perf` | 群已读推送需要 `OPENIM_WEBHOOK_SECRET` 和消息扩展开启 |
| open-im-server | `perf` | 群已读推送需要打开 `afterGroupMsgRead` webhook |

后端沿用当前健康实例即可（`local/openim-server:perf5-group-read-ready`、`local/openim-chat:perf5-group-read-push`）；如果重新部署，按 [GROUP_READ_PUSH_2026-11-18.md](GROUP_READ_PUSH_2026-11-18.md) 配置，并在结果里写明镜像。

### 启动 Web

开发服务（推荐，带诊断日志）：

```bash
cd example && EXPO_PUBLIC_OPENIM_ENTRY_TRACE=1 yarn start:openim:web
```

服务在 `http://localhost:35881/`。另外**至少用一次静态产物**复测第五节 J 组（刷新、深链接）：

```bash
cd example && EXPO_PUBLIC_OPENIM_ENTRY_TRACE=1 npx expo export --platform web
```

静态服务器必须把未知路径回退到 `index.html`，否则刷新详情页会 404（这是部署要求，不算产品缺陷，但要在结果里注明用的哪种服务）。

### 浏览器和账号

- 主测浏览器：桌面 Chrome 最新版（PC 和 H5 都用它，H5 用设备模拟）。抽查：macOS Safari、Edge 各走一遍 A、D、E 组。
- 多账号：Web 的登录态按**标签页**隔离（sessionStorage），同一浏览器的两个标签可以分别登录 A 和 B。需要"另一端"阅读或回复时，用另一个标签或另一个浏览器。
- 诊断：打开浏览器控制台，过滤 `IMEntry` / `IMReadPush`。日志不应包含账号 ID、群 ID、令牌或消息正文。
- 弱网 / 断网：Chrome DevTools → Network → Offline / Slow 3G。

## 三、本轮重点：11-17 之后的改动

这些改动是为手机端做的，但代码在浏览器上同样运行，需要逐项确认：

| 改动 | 浏览器上要确认的 | 对应用例 |
|---|---|---|
| 聊天页拆分为 `messages/ChatScreen/` 目录（发送、附件、历史、输入栏、提示条、已读、聚焦） | 聊天页每个功能都还在、行为不变 | D 组全部 |
| 消息行渲染器统一管理（`useChatRows`）、主题对象固定 | 消息气泡、菜单、表情回应、已读人数、通话卡片显示正确；一条消息变化时其他行不闪 | D4–D12、E1 |
| 已读人数：刚发的消息也会查询；收到服务端推送实时刷新 | **浏览器上第一次测实时推送** | E2–E5 |
| 通用页面（`ProductPage`）顶部安全区改由 JS 计算 | PC / H5 / iOS Safari 各页面顶部间距和以前一致，没有多出或缺少留白 | B6、各页面截图 |
| 通讯录加载时保持页面结构，只有好友行用骨架 | 首次进入通讯录时搜索框、新的朋友、群聊不跳 | F1 |
| 进入会话预热（按下即预加载）、转场动画 | 浏览器上点会话不卡、不白屏、不重复进入 | C2、J5 |
| 诊断开关统一（`shared/diagnostics.ts`） | 打开开关时控制台有 `[IMEntry]` / `[IMReadPush]`，关闭时没有 | E3、K2 |
| **用户反馈：PC 上切换页面有抖动、跳动** | 逐帧确认每类页面切换时有没有标题移动、整页平移、骨架结构替换、闪烁 | **M 组全部** |

### M 页面切换稳定性：抖动与跳动（PC 重点，H5 也做）

**用户反馈：PC 上点击切换页面时有抖动、跳动的感觉。** 这一组专门看切换过程中的画面，不看最终页面对不对（那是其他组的事）。

已针对其中两个原因改过（提交见结果文档的环境一节），本组同时验证这些修复：
- 首次加载：以前多个页面先显示一个通用骨架，数据到了再整页换成结构不同的内容。现在结构不依赖数据的页面直接显示真实结构，只对数据位置占位；其余页面的占位按页面形状绘制（M7）。
- 再次进入：页面进入时会重新拉取数据，以前拉取期间在内容顶部插入加载圈，把整页往下推再弹回。现在加载圈浮在内容上方，不占位置（M11）。

方法：
- 用录屏（或 DevTools → Performance 勾选 Screenshots）录下每次切换，**逐帧看点击后的前 500ms**，不要只看稳定后的截图。
- 每个页面分两种情况：**刷新后第一次进入**、**同一次打开里再次进入**；必要时用 DevTools Slow 3G 把加载拉长，让跳动更容易看清。
- 每次记录看到了哪一类现象（可多选）：
  - ①**标题、返回按钮或导航上下移动**；
  - ②**整页左右平移**（常见原因：内容变长出现滚动条，居中的内容被挤偏；Windows 浏览器滚动条占宽，更明显）；
  - ③**骨架整页替换成结构不同的真实内容**（例如骨架是头像列表，加载后变成卡片和设置项）；
  - ④**内容先出现再消失或闪一下**（例如空状态"还没有…"闪过）；
  - ⑤**右侧详情区宽度或位置变化**；
  - ⑥**侧栏选中高亮闪烁或先高亮错项**。
