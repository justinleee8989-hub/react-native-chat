# 进入会话耗时测试说明 · 第三轮（Android Release）— 2026-11-18

前两轮结果见 [`RESULTS_1.md`](RESULTS_1.md) 和 [`RESULTS_2.md`](RESULTS_2.md)。构建方法、抓日志方法和打点含义同 [`TEST_1.md`](TEST_1.md)。

测完后填写 [`RESULTS_3.md`](RESULTS_3.md)，原始日志放到 `docs/openim/evidence/2026-11-18-entry-perf-3/`，然后提交并推送到 `perf/openim-open-chat`。

## 一、第二轮遗留的问题

- **已预热的页面已经够快**：热进入长会话从点击到转场结束 548ms；改用 `ios_from_right` 动画后降到 288ms。
- **没预热的页面还是慢**（T2 来回切换会话、冷启动后第一次打开）：长会话要 530–655ms 才开始导航。日志显示，首次构建消息列表时 JS 连续卡了 380–440ms；同样这一步，短会话只卡约 110ms。
- **已读成员入口报错**：刚发出的消息还没有 `seq`，这时点"查看已读成员"会报"消息尚未同步"。

## 二、本轮改动

| 改动 | 对普通 Release 的影响 |
|---|---|
| **默认推入动画改为 `ios_from_right`**（会话列表 → 聊天页，以及 `chats` stack 内的其他页面） | **会生效**。第二轮实测动画约 172ms，原 `default` 约 450ms |
| **首次构建列表时只渲染视口内的行**（`drawDistance` 从 0 开始；转场结束后再扩到两屏，和以前一样） | **会生效**。目标是缩短没预热时首次构建那 380–440ms 的卡顿 |
| **已读成员入口**：消息还没有 `seq` 时，先从服务端历史里查出 `seq` 再跳转（和编辑、表情回应用的是同一套方法） | **会生效**。刚发出的消息点"查看已读成员"不应再报错 |
| **预热最近 3 个会话**（实验项，**默认仍为 1 个**）：列表获得焦点后依次准备最近 3 个有消息的会话，每个准备好后间隔 300ms 再准备下一个 | 只在诊断包里通过面板打开 |
| **日志新增 `rows` 字段**：`list-ready`、`navigate`、`transition-start`、`transition-end` 这几行会带上 `"rows":N`，表示这次点击以来消息行一共提交了多少次 | 只在诊断包里输出 |

诊断包面板现在有 6 个按钮：`进入`、`Activity`、`缓冲`、`动画`、`首屏`、`预热`。默认值是 `wait-ready` / `on` / `after-transition` / `ios_from_right` / `viewport` / `1`。

## 三、要测什么

先确认面板上的默认值是 `动画: ios_from_right`、`首屏: viewport`、`预热: 1`。

### U1 没预热时的首次构建（这一轮最关键）

用第二轮 T2 的步骤：冷启动后，依次打开 长 → 短 → 长 → 短，每次返回列表后等 1 秒。**按下面两种设置各做一组：**

| 组 | 首屏 | 说明 |
|---|---|---|
| U1a | `viewport`（默认） | 新行为 |
| U1b | `600` | 对照，相当于第二轮的 T2 |

每次打开请记：
- `navigate`、`list-ready`、`transition-end`；
- `navigate` 之前最大的 `long-frame`；
- `list-ready` 那一行的 `rows`。

### U2 预热 3 个会话

把面板切到 `预热: 3`，然后：
1. 返回列表，等 **3 秒**（让 3 个会话依次准备好）；
2. 依次打开列表里最近的 3 个会话，每次返回后都等 3 秒；
3. 记录每次是否预热命中，以及 `navigate`、`transition-end`。

**要确认的是：** 能否同时保留多个预热好的页面。如果第 2、3 个会话也是 `navigate` 在 30ms 以内，说明可以；如果它们的 `navigate` 仍要几百 ms，说明预热第二个会挤掉第一个，那就不考虑这个方案。

**另外留意：** 返回列表后的头 2–3 秒里，列表滚动会不会卡（因为后台在准备页面）。

### U3 热进入回归

默认设置下，长会话热进入 3 次。确认 `transition-end` 还在 300ms 左右，`首屏: viewport` 没有带来变慢。

## 四、功能回归

- [ ] **已读成员（本轮修复）**：在群聊里发一条新消息，**不要退出**，直接点气泡下面的"查看已读成员"，应能正常打开已读页面
- [ ] **已读人数实时刷新**：用**两台真机**（或两个真实客户端同时在前台），对方阅读后，本机当前页的已读人数应该**不用重新进入**就更新。第二轮用 API 标记已读，可能不会触发服务端推送的已读回执，所以这次请用真实客户端
- [ ] **首屏只渲染视口**：打开长会话后**马上**向上快速滑动，看看会不会出现空白行或闪烁
- [ ] **`ios_from_right` 动画**：进入、返回，以及从聊天页再进入设置页、已读页，动画都正常，没有闪黑或闪白
- [ ] 第二轮的其它回归项抽查一下：长按菜单、表情回应、名片、位置
- [ ] **失败重试**（第二轮没测到）：如果能造出"发送失败"的气泡，点一下重试，确认能重发成功
