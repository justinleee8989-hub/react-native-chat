## 一、本轮改动

| 第六轮的问题 | 原因 | 本轮改动 |
|---|---|---|
| V3 已读人数不实时刷新（服务端已确认发出） | **客户端只刷新本地已有 seq 的消息。** 页面要刷新的是"自己最新的一条群消息"，但挑选时要求本地 `seq > 0`。刚发出去的消息本地 seq 是 0（要等下一次同步才有，第三轮"消息尚未同步"就是同一原因），所以测试时那条新消息从来没被请求过已读人数，收到推送也只会刷新更早的一条。之后重新进入会话能看到 1，是因为那时 seq 已经同步 | 挑选"自己最新的一条"时不再要求本地 seq；没有 seq 的消息先从服务端历史查到 seq（和已读明细页、表情回应用的是同一个方法），再请求已读人数 |
| V3 设备端是否收到推送无法确认 | 没有客户端日志 | 诊断包里收到业务通知时打印一行 `[IMReadPush]`：数据类型、会话 ID、是否是已知群会话 |
| 首个会话静止进入时消息区下移再回位（3/3） | 转场结束时，第六轮同时做了三件事：扩大渲染缓冲、解除 30 条窗口、预取上一页，抖动正好出在这个时刻 | **撤回第五轮的预取和第六轮的 30 条窗口**，列表行为回到第四轮。这两项都没带来可测的收益：窗口没让未预热进入变快（364→364ms），预取针对的"等下一页"也已被证明不是空带的原因 |
| 通讯录首次进入：通用骨架整体换成不同结构的页面 | 首次加载时整页显示一个通用头像列表骨架，数据到了再换成搜索框、新的朋友、群聊、好友分组 | 搜索框、"新的朋友""群聊"和分组标题**第一帧就显示**；只有好友行在加载时用骨架占位。加载中不显示好友数量和"还没有好友" |

### 关于未预热进入仍为约 360ms

第六轮首屏行数与第四轮相同（28 行），但首屏构建帧从约 112ms 变成约 150ms；30 条窗口也没有改变它，说明不是消息条数的问题。第四轮到现在，列表相关代码已恢复为第四轮版本，变化的主要是**数据和后端**（新增的 QA 消息、表情和已读记录，后端镜像换成了 perf5）。请做下面的 V4b 对照，把代码因素和数据因素分开。

## 二、要测什么

### V3 群已读实时推送（重点）

方法同第六轮：Android 发一条新群消息后停在聊天页，H5 伙伴阅读，测两次。

记录：
- 已读人数从 0 变为 1 用了几秒（从 H5 点击算起）；
- logcat 里的 `[IMReadPush]` 行（`adb logcat | grep IMReadPush`）：是否出现、`known` 是否为 true；
- 另测一次"发完消息先退出聊天页再进入，然后伙伴阅读"，确认同样能实时刷新。

如果仍然不刷新，请附上 `[IMReadPush]` 是否出现：没出现说明设备没收到或原生层没转发；出现了且 `known: true` 说明问题在页面刷新这一段。

### V7 首个会话静止进入（复测第六轮补测）

方法同第六轮补测：冷启动 → 首次进入通讯录 → 回消息列表 → 点第一行长群，进入后不滚动不输入，3 次，看转场结束附近消息区是否上下移动。

### V6 通讯录首次进入（复测）

冷启动后首次进入通讯录 3 次，看最初 250ms：搜索框、新的朋友、群聊应该从第一帧就在原位，只有好友行从骨架变成真实内容，不再整页换结构。

### V4 速度回归

方法同第六轮，各 3 次（热进入 `transition-end`、长 → 短 → 长的未预热 `navigate`）。

### V4b 代码与数据对照（新增）

用同一台设备、同一个后端和账号，**在不清数据的前提下**，分别安装下面两个包，各测 3 次长 → 短 → 长的未预热 `navigate`：

1. 第四轮实现 `81c0b70` 构建的诊断 Release；
2. 本轮实现构建的诊断 Release。

两个包差不多，说明变慢来自数据或后端，不是代码；如果 `81c0b70` 明显更快，请把两组日志都附上。

### V1 快速上滑（只记录）

方法同第六轮，作为基线，本轮没有针对它的改动。

### V5 抽查
